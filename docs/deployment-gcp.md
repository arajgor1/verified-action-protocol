# Durable deployment on GCP

The canonical tested cloud path is GCP. This page describes the durable profile, the identities
it uses, and the staging rehearsal. All commands run in Cloud Build. No long-lived service account
keys are created or used.

> Status (v0.1.0-rc.1): the managed path below ran end to end in an existing project
> ([release/managed-staging-results.md](release/managed-staging-results.md)). Blank-project
> bootstrap is **excluded** from this release (see the last section of the steps).

## Topology

| Resource | Name | Identity | Notes |
|---|---|---|---|
| Cloud Run service | `vap-api-<env>` | `vap-api` | `--no-allow-unauthenticated`; app re-verifies the ID token (issuer, audience = service URL, expiry) |
| Cloud Run job | `vap-worker-<env>` | `vap-worker` | one execution per accepted operation (`run-operation <id>`); `--max-retries 0` so VAP owns retries |
| Cloud Run job | `vap-sweeper-<env>` | `vap-worker` | requeues missed outbox items and expired claims, expires request keys, applies retention |
| Cloud Scheduler | `vap-sweeper-<env>` | `vap-scheduler` | runs the sweeper every minute |
| Cloud Run job | `vap-migrate-<env>` | `vap-migrator` | applies migrations; the runtime identity has no DDL rights |
| Cloud SQL | `vap-<env>` | — | PostgreSQL 17, databases `vap` (journal) and `fixture`, PITR enabled |
| Secret Manager | `vap-<env>-database-url`, `-migration-database-url`, `-fixture-database-url`, `-digest-key` | — | generated by `managed-provision`, never printed |
| Cloud Storage | evidence bucket | — | uniform access, public access prevention, 30-day lifecycle |
| Artifact Registry | `vap` | the build identity writes | images referenced only by digest |
| Cloud Run service | `vap-fixture-<env>` | `vap-fixture` | staging gate only; synthetic data; public for the run; test controls on (owner-keyed faults for carol and dave; control listener on loopback only) |

## Identities

Two kinds of permission are involved, and they are held by different accounts:
- **Build and deployment permissions** create, deploy and delete the resources. They are held by
  the identity a Cloud Build run executes as, only while the pipelines run.
- **Application runtime permissions** are what the deployed services and jobs hold while they
  serve. They are held by the six exercise accounts below, each bound on one resource where
  Google Cloud allows it.

**Build and deployment**

| Identity | Authority |
|---|---|
| operator (human) | submits builds; prepares the project once (quickstart section 0) |
| build identity (verified runs) | the project's default Cloud Build service account, which in the verified project holds `roles/owner` |
| `vap-gate-provisioner`, `vap-gate-deployer` (prepared, not yet exercised) | dedicated build identities for the managed gate; see "Dedicated gate identities" |

**Application runtime**

| Identity | Authority |
|---|---|
| `vap-api` | Cloud SQL client (instance-conditioned), its two secrets, runs the worker job with overrides (that job only) |
| `vap-worker` | Cloud SQL client (instance-conditioned), its two secrets; connector credentials only |
| `vap-migrator` | Cloud SQL client (instance-conditioned) and the migration URL secret |
| `vap-fixture` | Cloud SQL client (instance-conditioned) and the fixture URL secret (staging only) |
| `vap-scheduler` | runs the sweeper job (that job only) |
| `vap-smoke` | invokes the staging API (that service only); the deploying identity may mint ID tokens for it. A test client, not part of a production deployment |

Database roles (created over SQL by `managed-provision`): `vap_runtime` has DML only on the
journal, `vap_migrator` owns database `vap`, `vap_fixture` owns database `fixture`; none is a
member of `cloudsqlsuperuser`.

Evidence artifacts of deployed services stay in the PostgreSQL artifact store; no runtime account
gets a role on the evidence bucket. The unsupported `bootstrap.sh` also defines `vap-ci-submitter`,
`vap-build`, `vap-release-builder`, `vap-deployer` and `vap-janitor`; the supported path does not
use them.

GitHub automation, if used, authenticates with Workload Identity Federation restricted to the
repository and protected refs (`.github/workflows/cloud-test.yml`), never with stored keys.

## Managed staging in an existing project (supported)

This path ran end to end ([release/managed-staging-results.md](release/managed-staging-results.md)).

**Exact prerequisites** (in addition to the quickstart's section 0):

| Prerequisite | Detail |
|---|---|
| APIs | `run`, `artifactregistry`, `sqladmin`, `sql-component`, `secretmanager`, `cloudscheduler`, `iamcredentials`, `cloudresourcemanager` (all `*.googleapis.com`), plus the quickstart's three |
| Artifact Registry | a Docker repository named `vap` in the build region (`bash scripts/vap-cloud.sh release` pushes the images there) |
| Build identity | **The verified runs used the project's default build identity, which holds `roles/owner`.** A narrower setup is prepared but has not run: two dedicated identities, see "Dedicated gate identities" below and [release/managed-gate-identity-plan.md](release/managed-gate-identity-plan.md). An earlier draft of this table listed unconditioned `roles/iam.serviceAccountAdmin`, project-wide `roles/iam.serviceAccountUser` and `roles/resourcemanager.projectIamAdmin` for one identity; each of those lets the holder reach the project's Owner-level identities, so that list was not least privilege and is withdrawn |
| Organization policy | the synthetic fixture is deployed with `--allow-unauthenticated`; a domain-restricted-sharing policy would block it |
| Spending | Cloud SQL bills while it exists (about $0.013 an hour at the provisioned size); billing alerts are notifications, not caps |

**Steps:**

1. `bash scripts/vap-cloud.sh managed-provision --expires <unix seconds>`: service accounts, Cloud
   SQL with least-privilege roles created over SQL, secrets and instance- or resource-scoped IAM
   (`infra/gcp/cloudbuild.managed-provision.yaml`). It creates no deployer account and no
   project-level Run or Scheduler role.
2. `bash scripts/vap-cloud.sh release`, then
   `bash scripts/vap-cloud.sh deploy --image <region>-docker.pkg.dev/<project>/vap/vap@sha256:<digest>`:
   the managed deployment gate (`infra/gcp/cloudbuild.deploy.yaml`). Its checks never skip its own
   teardown of the Cloud Run services, jobs and scheduler.
3. `bash scripts/vap-cloud.sh managed-teardown`: deletes Cloud SQL (no final backup), the secrets,
   the bindings and the service accounts, then verifies by listing. Google Cloud has no expiry
   for these resources; `--expires` is only recorded as a label, so the operator must run the
   teardown (or schedule it) by that time. If the listing still shows a just-deleted account
   (IAM listing is eventually consistent), run it again.

## Dedicated gate identities (prepared, not yet exercised)

**Use this script only in a project dedicated to the exercise.**

**Targeting.**
- In `765be87`, some of the script's commands omitted `--project` and acted on gcloud's active
  project. This was a defect found in the Plan B run.
- The successor candidate fixes it. The script requires `VAP_GCP_PROJECT` and passes it to every
  project-dependent command, in both `create` and `remove`. It never reads or changes the gcloud
  configuration.
- Before the first change, it stops if any of these fails:
  - the project exists and is ACTIVE;
  - its id matches, and its number matches when `VAP_GCP_PROJECT_NUMBER` is given;
  - for `create`, the build bucket and the `vap` repository are in that project.
- A unit test checks this against a deliberately different active project. Its first cloud run
  (on `4d50c16`) failed because of a defect in the test; a corrected test is prepared but has not
  run ([release/publication-plan.md](release/publication-plan.md), section 7).

**Permissions.** In a shared project, the script leaves
project-wide service-account deletion and act-as administration over every account in the
project. The revised plan for the final gate
([release/managed-gate-identity-plan.md](release/managed-gate-identity-plan.md)) recommends
running the script unchanged in a disposable project that is deleted afterwards (Plan B). It
also gives an in-project alternative without those two permissions (Plan A). Neither has been
applied.

`infra/gcp/gate-identities.sh create` (run by the project owner with their own credentials)
creates two build identities so the managed gate does not run as the default build identity.
Builds run as one of them when `VAP_BUILD_SERVICE_ACCOUNT` names it for `scripts/vap-cloud.sh`.
The bindings are derived from the pipelines' commands; the run itself is the test, and any
missing permission will surface as a failed step (the gate's teardown steps still run).

| Identity | Runs | Project-level roles (condition) | Resource-level roles |
|---|---|---|---|
| `vap-gate-provisioner` | `managed-provision --deployer vap-gate-deployer@…` | `iam.serviceAccountCreator`; `iam.serviceAccountAdmin` (may only grant `serviceAccountUser` and `serviceAccountOpenIdTokenCreator`); `resourcemanager.projectIamAdmin` (may only grant `cloudsql.client`); `cloudsql.admin`; `secretmanager.admin`; `logging.logWriter` | build bucket: `storage.objectViewer`, `storage.objectCreator` |
| `vap-gate-deployer` | `deploy`, `managed-teardown` | `run.admin`; `cloudscheduler.admin`; `cloudsql.admin` (instance `vap-<env>` only); `cloudsql.viewer`; `secretmanager.admin` (secrets `vap-<env>-*` only); `secretmanager.secretAccessor` (`vap-<env>-database-url` only); `secretmanager.viewer`; `iam.serviceAccountViewer`; `iam.serviceAccountDeleter`; `resourcemanager.projectIamAdmin` (may only grant `cloudsql.client`); `iam.securityReviewer`; `logging.viewer`; `logging.logWriter` | build bucket: `storage.objectViewer`, `storage.objectCreator`; repository `vap`: `artifactregistry.reader`; granted by provisioning on each account only: `iam.serviceAccountUser` on `vap-api`, `vap-worker`, `vap-migrator`, `vap-fixture`, `vap-scheduler`, and `iam.serviceAccountOpenIdTokenCreator` on `vap-smoke` |

The submitting principal also needs `iam.serviceAccountUser` on each of the two identities
(granted by the script on those accounts only).

**What this separation prevents, and what it does not.** Neither identity holds Owner, Editor,
`serviceAccountTokenCreator` or project-wide act-as, and neither can grant itself other project roles. The
deployer can act only as the five runtime accounts, so it cannot run code as the Owner-level
default identities. Remaining authority to be aware of:
- the provisioner's conditioned `serviceAccountAdmin` applies to every service account in the
  project, so it could grant act-as or ID-token minting on any of them (including the default
  identities) to anyone. It holds no Run, Scheduler or Cloud Build role with which to use act-as
  itself. A resource-name condition cannot close this: IAM does not evaluate resource attributes
  for service accounts. Plan A in the revised plan avoids the role instead;
- the deployer can modify or delete any Cloud Run service, job or scheduler job in the project,
  and delete any service account (`serviceAccountDeleter` has no resource condition);
- both can read every object in the build bucket, including the evidence prefix;
- the role-grant conditions (`modifiedGrantsByRole`) and resource conditions fail closed if IAM
  does not support them for a call: the step is denied rather than allowed.

## Blank-project bootstrap: excluded from v0.1.0-rc.1

`infra/gcp/bootstrap.sh` (with `infra/gcp/teardown.sh`) has never run from a blank project and is
not supported in this release; it refuses to run unless `VAP_ALLOW_UNSUPPORTED_BOOTSTRAP=1` is
set. Known defects, found by the managed exercise and not fixed because they could not be tested
without a new billed project:
- users created with `gcloud sql users create` become members of `cloudsqlsuperuser`, so the
  runtime role would not be least privilege (the supported path creates roles over SQL);
- it gives `vap-deployer` project-level `run.admin` and `cloudscheduler.admin` (the supported path
  deploys as the build identity and scopes every grant to one resource).
The missing APIs it had (`sql-component`, `iamcredentials`, `cloudresourcemanager`) were added to
its list.

## Verify a release image

Release images are referenced by digest. Cloud Build records signed SLSA v1 provenance for each
(Container Analysis API required). It names the building project, identity and storage, so for
v0.1.0-rc.1 it is kept private: it is not published, and an edited copy would no longer verify.
An operator who builds in their own project can inspect their own provenance before deploying:

```bash
gcloud artifacts docker images describe <region>-docker.pkg.dev/<project>/vap/vap@sha256:<digest> --show-provenance
```

Check that the builder is `https://cloudbuild.googleapis.com/GoogleHostedWorker`, that the resolved
dependencies list the pinned base-image digests from `toolchain.json`, and that the source matches
the archive of the release commit. The release evidence (`SHA256SUMS`, SBOMs, scan reports) sits
next to the build in the private evidence location.

## Configuration

Runtime variables are listed in `.env.example`. Required in production: `VAP_DATABASE_URL`
(secret), `VAP_DIGEST_KEY` (secret, at least 32 characters), `VAP_OIDC_AUDIENCE`. Startup fails
if demo authentication or isolated test mode is enabled in production, or if the schema is not
at the build's latest migration.

## Migrations and rollback

Migrations are append-only, checksummed and applied by the migration job under an advisory
lock. A build refuses to run against a database with a newer migration than it knows, and a
modified migration fails the run. Roll back the application by deploying the previous image
digest; never reverse destructive schema changes blindly. Restore drills must show that
unresolved submissions remain `unknown` and are reconciled, never replayed
(`tests/faults/restore.test.ts`).

## Spending controls

Before any cloud execution, the operator decides the project, region, authorized resources,
concurrent job cap and spend ceiling. Defaults proposed here: two concurrent test builds,
30-minute build timeout, `db-f1-micro` Cloud SQL, at most 3 API instances. Billing alerts are not
hard caps; stop new work at the configured boundary and tear down staging after rehearsals.

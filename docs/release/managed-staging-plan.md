## 2. Identity and IAM changes

All of these are created by `bootstrap.sh` or the deploy pipeline. Each is scoped to the named
account or resource.

| Principal | Role | Scope | Why |
|---|---|---|---|
| `vap-api`, `vap-worker`, `vap-migrator`, `vap-fixture` | `roles/cloudsql.client` | project | connect to Cloud SQL through the connector |
| `vap-api`, `vap-worker` | `roles/secretmanager.secretAccessor` | the `database-url` and `digest-key` secrets only | runtime configuration |
| `vap-migrator` | `roles/secretmanager.secretAccessor` | the `migration-database-url` secret only | migrations |
| `vap-fixture` | `roles/secretmanager.secretAccessor` | the `fixture-database-url` secret only | fixture database |
| `vap-api`, `vap-worker` | `roles/storage.objectAdmin` | evidence bucket only | evidence artifacts |
| `vap-api` | `roles/run.jobsExecutorWithOverrides` | the `vap-worker-staging` job only | dispatch one worker execution per operation |
| `vap-scheduler` | `roles/run.invoker` | project (bootstrap) | trigger the sweeper |
| `vap-deployer` | `roles/run.admin`, `roles/cloudscheduler.admin` | project | create and delete the services, jobs and scheduler |
| `vap-deployer` | `roles/iam.serviceAccountUser` | the `vap-api`, `vap-worker`, `vap-migrator` and `vap-fixture` accounts only | deploy services and jobs that run as them |
| `vap-deployer` | `roles/logging.logWriter` (project); `roles/storage.objectCreator` (evidence bucket) | as stated | the deploy build's own logs and evidence |
| **`vap-deployer`** | **`roles/iam.serviceAccountOpenIdTokenCreator`** | **the `vap-smoke` account only** | mint Google-signed ID tokens for the smoke identity (see below) |
| `vap-smoke` | `roles/run.invoker` | the `vap-api-staging` service only (granted by the deploy pipeline) | call the IAM-protected API |
| the submitting operator | `roles/cloudbuild.builds.editor`; `roles/iam.serviceAccountUser` on `vap-deployer` only | as stated | submit the deploy build as `vap-deployer` |

**Narrowest permission for the token-minting step.** The smoke test needs a Google-signed ID
token whose audience is the service URL and which carries a verified email claim.

- **Why minting is needed at all:** Cloud Build has no metadata identity endpoint (confirmed:
  HTTP 404), and `gcloud ... --include-email` refuses its credentials, so the build cannot simply
  read its own ID token.
- **What is needed:** the IAM Credentials `generateIdToken` call needs only
  `iam.serviceAccounts.getOpenIdToken` on the **target** account. That permission is in
  `roles/iam.serviceAccountOpenIdTokenCreator`, granted to `vap-deployer` on `vap-smoke` alone.
  `roles/iam.serviceAccountTokenCreator` would also allow access tokens, `signBlob` and `signJwt`,
  so it is not used.
- **Why a separate smoke identity:** minting for `vap-smoke` rather than for the deployer keeps a
  leaked token to an identity that can only invoke this one service, with VAP roles it holds only
  in this staging deployment.
- **Alternative with no minting permission at all:** run the smoke client as a Cloud Run job under
  `vap-smoke`. Cloud Run's metadata server issues ID tokens natively. This needs a smoke-client
  image, which does not exist yet.

## 4. Tests in the managed rehearsal

| Requirement | Test |
|---|---|
| Google-signed authentication | Cloud Run IAM plus VAP's OIDC verification of a Google-signed token for `vap-smoke` (audience = service URL). An unauthenticated request must be rejected (smoke `basic`), and a Google-signed token with the wrong audience must be rejected (deploy step `identity`) |
| Migrations | `vap-migrate-staging` job as `vap_migrator`; the API refuses to start if the schema is not current |
| Dispatch | API in `cloud-run-job` mode starts one `vap-worker-staging` execution per operation; the smoke operation must end `verified` |
| Restart recovery | an operation is started, then the API gets a new revision (restart) and the latest worker execution is cancelled mid-flight |
| Reconciliation | the sweeper job runs. The interrupted operation must end `verified`, or honestly `unknown`, never resubmitted without a `reconcile.result` event (smoke `check`) |
| Journal durability | operations survive the API restart in Cloud SQL (`check` reads them after the restart) |
| Cleanup | the deploy pipeline deletes its services, jobs and scheduler, then fails if any Cloud Run resource labelled with the run id remains. `teardown.sh` deletes Cloud SQL and the secrets |

The runtime role's DDL refusal and the SIGKILL of database containers are covered by the
ephemeral rehearsal only. A managed database cannot be killed that way.

## 5. Teardown and what persists

1. The deploy pipeline's `teardown` step (default) deletes both Cloud Run services, the three
   jobs and the scheduler job, then verifies by label.
2. `VAP_GCP_PROJECT=... VAP_GCP_REGION=... VAP_ENVIRONMENT=staging VAP_DELETE_DATABASE=true bash infra/gcp/teardown.sh`
   deletes the Cloud SQL instance and the four secrets, and reports each deleted, retained or
   failed resource.
3. **What persists:**
   - the service accounts and their IAM bindings (no cost; delete with
     `gcloud iam service-accounts delete vap-<name>@<project>.iam.gserviceaccount.com`);
   - Artifact Registry images;
   - the evidence bucket (30-day lifecycle).
